3. Stworzenie klasy danych i tymczasowego źródła danych
W pierwszej kolejności stworzymy klasę reprezentującą nasze zadania do wykonania. Zadanie będzie posiadało: nazwę, opis, oznaczenie zakończenia i ważności. Dodatkowo w postaci identyfikatora będzie przechowywany znacznik czasowy stworzenia zadania.

Klasa Task
Task.kt
/**
* Data class representing a task. Data classes are special classes in Kotlin that are used to
* represent data, the benefits of using a data class are that it automatically generates
* `equals()`, `hashCode()`, `toString()`, and `copy()` methods for you.
*
* @param name The name of the task.
* @param description The description of the task.
* @param isCompleted The completion status of the task.
* @param isImportant The importance status of the task.
* @param taskId The unique ID of the task (also a timestamp of creation).
*/
data class Task(
   var name: String,
   var description: String,
   var isCompleted: Boolean = false,
   var isImportant: Boolean = false,
   val taskId: Long = System.currentTimeMillis()
)

Klasa jest oznaczona jako data, jest to typowe oznaczenie dla klas, które mają reprezentować dane. Dzięki słowu kluczowemu data w klasie Task zostaną automatycznie wygenerowane metody equals(), hashCode(), toString() i copy(). Do tworzenia znaczników czasowych wykorzystano funkcję systemową currentTimeMillis() zwracającą czas w milisekundach (typ Long) od tzw. epoki unix (ang. Unix Epoch) czyli od 1 stycznia 1970 r.

Obiekt DataSource
Drugim elementem związanym z danymi będzie obiekt DataSource. Będzie on służył jako tymczasowe źródło danych, do momentu dodania relacyjnej bazy danych w późniejszych krokach instrukcji. DataSource jest zaimplementowane jako object ponieważ nie ma konieczności tworzenia więcej niż jednej instancji źródła danych. W kontekście źródeł danych bardzo ważną zasadą jest zasada pojedynczego źródła prawdy (ang. Single Source of Truth)

DataSource.kt
/**
* A simple object to hold the list of tasks and allows for creating dummy content.
* It will be replaced by a database later on.
*/
object DataSource {
 /** A list of tasks. */
   private val tasks = mutableListOf<Task>().apply { addAll(getDummyContent(2)) }
   /**
    * Get a list of tasks with dummy content.
    * @param numElements the number of tasks to generate
    * @return a list of tasks
    */
   fun getDummyContent(numElements: Int): List<Task> {
       val list = mutableListOf<Task>()
       for (i in 0 until numElements) {
           // Create a task with a unique ID using the current time in milliseconds and some
           // default values for the name and description
           list.add(
               Task(
                   name = "Task $i",
                   description = "Description $i",
                   taskId = System.currentTimeMillis() + i * 1000
               )
           )
       }
       return list
   }
     /**
    * Add a task to the list.
    * @param task the task to add
    */
   fun addTask(task: Task) {
       tasks.add(task)
   }
   /**
    * Get the list of tasks.
    * @return the list of tasks
    */
   fun getTasks(): List<Task> {
       return tasks
   }
   /**
    * Delete a task from the list.
    * @param task the task to delete
    */
   fun deleteTask(task: Task) {
       tasks.remove(task)
   }
   /**
    * Update a task in the list.
    * @param task the task to update
    */
   fun updateTask(task: Task) {
       // Find the index of the task with the same ID as the updated task
       val index = tasks.indexOfFirst { it.taskId == task.taskId }
       // If the task is found the index will be greater than -1
       if (index != -1) {
           // Replace the task at the index with the updated task
           tasks[index] = task
       }
   }
   /**
    * Get a task from the list by ID.
    * @param id the ID of the task to get
    * @return the task with the given ID
    */
   fun getTask(id: Long): Task {
       // Find the task with the given ID using the first() function to return the first task
       // that matches the predicate: it.taskId == id
       return tasks.first { it.taskId == id }
   }
}

W obiekcie DataSource znajdują się:

zmienna tasks przechowująca listę zadań. Zmienna jest prywatna by wszelkie modyfikacje były możliwe tylko z "poziomu" obiektu.
Blok apply w Kotlinie jest jedną ze specjalnych funkcji typu scope, która pozwala skonfigurować obiekt natychmiast po jego utworzeniu. Zwraca ona ten sam obiekt, na którym została wywołana.

Standardowa biblioteka Kotlin zawiera kilka funkcji typu scope, których jedynym celem jest wykonanie bloku kodu w kontekście obiektu. Więcej można przeczytać na stronie: Scope functions | Kotlin Documentation

funkcja getDummyContent tworząca przykładowe elementy listy. Funkcja nie dodaje ich bezpośrednio do zmiennej tasks tylko zwraca nową listę
funkcje add, delete, update, get pozwalają na modyfikacje i odczyt zmiennej tasks i realizują typowe operacje CRUD (ang. Create Read Update Delete)
W funkcjach updateTask i getTask wykorzystano funkcje first oraz indexOfFirst ich działanie jest podobne tzn. na podstawie podanego warunku (np. it.taskId == id) znajdują pierwszy element lub indeks pierwszego elementu spełniającego ten warunek

Ekran listy
Posiadając już zdefiniowany wygląd pojedynczego elementu listy można go wykorzystać w liście. W Compose listy pionowe realizowane są za pomocą funkcji kompozycyjnej LazyColumn, natomiast poziome za pomocą LazyRow. Te funkcje renderują tylko te elementy, które są widoczne na ekranie oszczędzając zasoby w szczególności w przypadku długich list.

Do funkcji kompozycyjnej ToDoListScreen dodaj następujący kod

ToDoListScreen.kt
Surface(
   modifier = modifier.padding(8.dp)
) {
   Column {
       LazyColumn(
           modifier = Modifier
               .padding(bottom = 8.dp)
       ) {
           items(
               items = DataSource.getTasks(),
           ) { task ->
               TaskItem(
                   task = task,
                   onEditClick = {},
                   onDelete = {},
                   onCheckedChange = {}
               )
           }
       }
   }
}

Informacja: LazyColumn zawarte jest w dodatkowych funkcjach kompozycyjnych Surface i Column, które będą potrzebne później

Uwaga: Dodaj powyższy import do pliku ToDoListScreen jeżeli element items będzie podkreślony:

import androidx.compose.foundation.lazy.items
Funkcja items ma kilka implementacji i jej domyślna wersja zakłada przekazywanie liczby elementów do wyświetlenia, a nie listę jak w przykładzie powyżej.



Funkcja items wewnątrz LazyColumn (lub LazyRow) służy do wydajnego renderowania listy elementów. Działa jak pętla, która iteruje po kolekcji i tworzy funkcje kompozycyjne dla każdego elementu. W tym przypadku lista elementów pobierana jest z obiektu DataSource za pomocą funkcji getTasks().

Sprawdź w funkcji podglądu czy lista wyświetla się prawidłowo. Na tym etapie nie ma możliwości interakcji z listą.
5. Interakcja z listą
Bardzo często LazyColumn nie tylko wyświetla użytkownikowi zawartość kolekcji, ale i umożliwia mu interakcje z pojedynczymi elementami jak i z całą listą. W tej części zajmiemy się zagadnieniami z tym związanymi. Implementacja interakcji, oprócz przypadku rozwijania elementu, polega na wyniesieniu zdarzeń na elemencie listy do komponentu wyżej w hierarchii poprzez funkcje lambda w parametrach elementu TaskItem.

Rozwinięcie opisu
Pierwszą interakcją, którą się zajmiemy będzie rozwijanie opisu zadania. W tym celu do modyfikatora komponentu Surface w TaskItem dodaj:

Surface(
   modifier = modifier
       .fillMaxWidth()
       .padding(8.dp)

Na tym etapie funkcjonalność oznaczenia zadania jako ukończone nie będzie działać poprawnie. Dzieję się tak ponieważ funkcja ToDoListScreen nie posiada stanu, który mógłby powodować rekompozycje. Kliknięcie w przycisk edycji
Kolejnym elementem jest implementacja funkcjonalności edycji realizowana w reakcji na naciśnięcie ikony edycji w elemencie listy. W pierwszej kolejności musimy w przycisku edycji w TaskItem przypisać zdarzenie dla parametru onClick. W tym przypadku będzie to wywołanie funkcji lambda onEditClick przekazywanej do funkcji kompozycyjnej TaskItem.

ToDoListScreen.kt
IconButton(onClick = onEditClick) {
   Icon(Icons.TwoTone.Edit, contentDescription = "Edit Task")
}
Funkcjonalność edycji będzie realizowana przez osobną funkcję kompozycyjną, więc musimy mieć możliwość przekazania do niej zadania, które ma być edytowane. W tym celu funkcjonalność edycji jest wynoszona z elementu ToDoListScreen przez dodanie do jej sygnatury funkcji lambda onEdit przyjmującej typ Task jako parametr. Następnie wywołanie funkcji onEdit przekazywane jest do parametru onEditClick elementu TaskItem. W ten sposób kliknięcie w przycisk edycji w konkretnym elemencie listy wywoła implementacje funkcji onEdit z odpowiednim zadaniem (zagadnieniem edycji zajmiemy się na dalszym etapie instrukcji).

ToDoListScreen.kt
@Composable
fun ToDoListScreen(modifier: Modifier = Modifier,  onEdit: (Task) -> Unit = {},) {
   Surface(
       modifier = modifier.padding(8.dp)
   ) {
       Column {
           LazyColumn(
               modifier = Modifier
                   .padding(bottom = 8.dp)
           ) {
               items(items = DataSource.getTasks()) { task ->
                   TaskItem(
                       task = task,
                       onEditClick = {onEdit(task)},
                       onDelete = {},
                       onCheckedChange = {DataSource.updateTask(task.copy(isCompleted = it))}
                   )
               }
           }
       }
   }
}

Następnie w funkcji TaskItem wywołanej w LazyColumn zaimplementuj funkcję lambda onDelete:

) {
   items(items = DataSource.getTasks()) { task ->
       TaskItem(
           (...),
           onDelete = {
               showDeleteDialog = true
               taskToDelete = task
           },
           (...)
       )
   }
}

6. Okna dialogowe
Jednym ze sposobów tworzenia okien dialogowych jest wykorzystanie funkcji kompozycyjnej AlertDialog (lub BasicDialog). Składa się on z następujących elementów:

Stwórz funkcję kompozycyjną:

@Composable
fun DeleteConfirmationDialog(
   task: Task,
   onConfirm: () -> Unit,
   onDismiss: () -> Unit
) {
   AlertDialog(
       onDismissRequest = onDismiss,
       title = { Text(stringResource(R.string.delete_task_title)) },
       text = { Text(stringResource(R.string.delete_msg, task.name)) },
       confirmButton = {
           TextButton(onClick = onConfirm) {
               Text(stringResource(R.string.delete), color = Color.Red)
           }
       },
       dismissButton = {
           TextButton(onClick = onDismiss) {
               Text(stringResource(R.string.cancel))
           }
       }
   )
}
Uwaga: Pamiętaj o zdefiniowaniu stringów w strings.xml

Najważniejsze elementy:

Wyniesienie reakcji na przyciski confirm oraz dismiss do rodzica tej funkcji kompozycyjnej. Jest to zrealizowane przez funkcje lambda onConfirm i onDismiss w sygnaturze DeleteConfirmationDialog wywoływane w parametrach confirmButton oraz dismissButton elementu AlertDialog
Dzięki parametrowi onDismissRequest możemy zdecydować co się stanie gdy użytkownik będzie chciał odrzucić komunikat (poprzez kliknięcie wstecz lub poza obszar okna dialogowego)
parametry title, text, confirmButton, dismissButton mają typ funkcji kompozycyjnej możemy więc w ten sposób tworzyć praktycznie dowolne okna dialogowe

Każda rekompozycja z wartością zmiennej showDeleteDialog równą true oraz wartością taskToDelete różną od null wyświetli okno dialogowe z danymi zadania, które zostało przytrzymane.

Reakcja na przyciski okna
Jak zostało wspomniane wcześniej reakcja na przyciski confirm i dismiss została wyniesiona z funkcji DeleteConfirmationDialog po to by rodzic "wiedział", którą akcję wybrał użytkownik.

W parametrach onConfirm i onDismiss dodaj poniższy kod:

ToDoListScreen.kt
onConfirm = {
   DataSource.deleteTask(taskToDelete!!)
   taskToDelete = null
   showDeleteDialog = false
},
onDismiss = {
   taskToDelete = null
   showDeleteDialog = false
}
W przypadku funkcji w parametrze onConfirm wywołujemy metodą usuwania zadania z obiektu DataSource. W obu przypadkach zmieniamy również stan funkcji kompozycyjnej ToDoListScreen poprzez ustawienie zmiennych showDeleteDialog na false a taskToDelete na null, co spowoduje rekompozycje i ukrycie okna dialogowego.

Testowanie usuwania elementów z listy
Przetestuj teraz funkcjonalność usuwania.
7. Ekran dodawania/edycji zadań
W dalszych krokach zajmiemy się przygotowanie ekranu do dodawania/edycji zadań. Będzie on zaimplementowany w pliku AddEditScreen.

Stwórz interfejs użytkownika podobny do:

* A composable function that displays the Add/Edit screen.

* @param onSave The callback that is called when the task is saved.
* @param onCancel The callback that is called when the task is canceled.

@Composable

Gdzie task to opcjonalna zmienna zadania, które chcemy edytować. W przypadku gdy ta zmienna ma wartość różną od null dane z przekazywanego zadania są wstępnie wpisywane w formularzu, w przeciwnym wypadku formularz jest inicjowany jako pusty. Zwróć uwagę, że funkcja onSave jako parametr przyjmuje obiekt typu Task, dzięki czemu w kodzie wywołującym element AddEditScreen możemy operować na gotowej instancji klasy Task.

Do przechowywania stanu UI posłużymy się następującymi zmiennymi:

var description by remember { mutableStateOf(task?.description ?: "") }
var isImportant by remember { mutableStateOf(task?.isImportant == true) }
var validationError by remember { mutableStateOf(false) }
Pierwsze trzy są bezpośrednio związane z wprowadzanym zadaniem, natomiast validationError jest flagą oznaczającą błąd w formularzu (w przypadku gdy pola name i description są puste). Zwróć uwagę na inicjalizację zmiennych name, description i isImportant, wszystkie korzystają z operatorów związanych z bezpieczeństwem wartości null (operatory ? i ?: ), które zabezpieczają przed wyjątkiem nullPointerException.

OutlinedTextField z przyciskiem kasuj
Jednym z głównych elementów formularza wprowadzania/edycji zadania są pola tekstowe. Korzystaliśmy już z nich przy okazji pierwszego ćwiczenia. W tym zadaniu dodana została jeszcze często spotykana funkcjonalność polegająca na dodaniu ikony modyfikującej zawartość pola tekstowego, w tym przypadku będzie to czyszczenie pola.

Stwórz funkcję kompozycyjną OutlinedTextFieldWithClearAndError:

AddEditScreen.kt
/**
* A composable function that displays an [OutlinedTextField] with a clear button and an error message.
* @param value The value of the text field.
* @param onValueChange The callback that is called when the value changes.
* @param label The label of the text field.
* @param errorMessage The error message to display.
* @param isError Whether the text field is in an error state.
* @param modifier The modifier to apply to the text field.
* @param singleLine Whether the text field should be single line.
*/
@Composable
fun OutlinedTextFieldWithClearAndError(
   value: String,
   onValueChange: (String) -> Unit,
   label: String,
   errorMessage: String,
   isError: Boolean,
   modifier: Modifier = Modifier,
   singleLine: Boolean = true,
) {
   OutlinedTextField(
       value = value,
       onValueChange = onValueChange,
       label = { Text(label) },
       singleLine = singleLine, // this is lifted to the caller to make it more reusable
       trailingIcon = {
           // The clear button is only displayed when the text field is not empty

                   onClick = {

                       contentDescription = stringResource(
                           R.string.clear_content_description,
                           label
                       )
                   )
               }
           }
       },
       isError = isError,
       supportingText = {
           Row {
               if (isError)
                   Text(errorMessage)
           }
       },
       modifier = modifier
   )
}

Funkcja ta może być wykorzystana zarówno dla zmiennej name jak i description. W tym celu parametr singleLine elementu OutlinedTextField jest wyniesiony do parametru funkcji OutlinedTextFieldWithClearAndError, co pozwala na zmianę tego parametru w zależności od potrzeb. Dla pola name, singleLine będzie miało wartość true, natomiast w przypadku description będzie to false.

Kliknięcie w ten przycisk spowoduje przekazanie do pola tekstowego pustego ciągu znaków co spowoduje rekompozycje i wyczyszczenie pola.

Switch z tekstem
Innym nowym elementem UI jest Switch. Jego podstawowa implementacja nie pozwala na dodanie informacji tekstowej informującej do czego przełącznik służy. Dlatego stworzymy prostą funkcję kompozycyjną

AddEditScreen.kt
/**
* A composable function that displays a [Switch] with a text label.
* @param text The text to display next to the switch.
* @param checked The checked state of the switch.
* @param modifier The modifier to apply to the row.
* @param onCheckedChange The callback that is called when the switch is toggled.
*/
@Composable
fun SwitchWithText(
   text: String,
   checked: Boolean,
   modifier: Modifier = Modifier,
   onCheckedChange: (Boolean) -> Unit
) {
   Row(
       modifier = modifier.fillMaxWidth(),
       horizontalArrangement = Arrangement.End,
       verticalAlignment = Alignment.CenterVertically,
   )
   {
       Text(text)
       // add some space between the text and the switch, could also be done with padding
       Spacer(modifier = Modifier.padding(8.dp))
       // The switch composable the most important parameters are checked and onCheckedChange
       // checked is the state of the switch and onCheckedChange is the callback that is called
       // when the switch is toggled
       Switch(checked = checked, onCheckedChange = onCheckedChange)
   }
}
Najważniejszym elementem tej funkcji jest Switch, do jego obsługi służą parametry checked (oznaczenie aktualnego stanu przełącznika) oraz funkcja onCheckedChange pozwalająca na dodanie reakcji na zmiany stanu przełącznika. Oba te elementy są wyniesione z samej funkcji aby mieć do nich dostęp z funkcji kompozycyjnej będącej jej rodzicem (podobnie jak to miało miejsce w przypadku kilku wcześniejszych funkcji kompozycyjnych). W przedstawionym na początku sekcji przykładzie funkcja SwitchWithText została wywołana w następujący sposób:

SwitchWithText(
   text = stringResource(R.string.important_label),
   checked = isImportant
) { isImportant = it }
Informacja: Funkcja lambda onCheckedChange jest zaimplementowana w formie trailing lambda, stąd brak tego argumentu bezpośrednio w wywołaniu.

8. Komponent nawigacji
Mając stworzone już wszystkie ekrany przejdziemy do implementacji nawigacji wewnątrz aplikacji. Nowoczesne aplikacje wieloekranowe są tworzone przy użyciu komponentu Jetpack Navigation, podobnie jak w przypadku tworzenia interfejsów użytkownika, w sposób deklaratywny.

Komponent Nawigacji składa się z trzech głównych części:

NavController: Odpowiedzialny za nawigację między ekranami w aplikacji.
NavGraph: Odwzorowuje miejsca docelowe (ekrany), do których można nawigować.
NavHost: Funkcja kompozycyjna będąca kontenerem do wyświetlania bieżącego miejsca docelowego wskazywanego przez NavGraph.
Konfiguracja skryptów Gradle - dodanie zależności
Aby móc skorzystać z Komponentu Nawigacji należy dodać odpowiednie zależności w skryptach Gradle.

Przejdź do pliku libs.versions.toml i dodaj następujące wpisy:

W sekcji [versions] dodaj:

navigationCompose = "2.8.9"
W sekcji [libraries] dodaj

androidx-navigation-compose = { module = "androidx.navigation:navigation-compose", version.ref = "navigationCompose" }
Następnie wykonaj synchronizację. Po zakończeniu przejdź do pliku build.gradle dla modułu app i dodaj zależność (w sekcji dependencies):

implementation(libs.androidx.navigation.compose)
i zsynchronizuj projekt jeszcze raz. Dzięki tym krokom będziemy mogli skorzystać z Jetpack Navigation Compose.

Stworzenie ścieżek
Jedną z podstawowych koncepcji w odniesieniu do nawigacji w aplikacjach Compose jest trasa (ang. route). Trasa to ciąg znaków odpowiadający miejscu docelowemu. Można się tutaj posłużyć analogią do koncepcji adresu URL. Podobnie jak różne adresy URL prowadzą do różnych podstron na stronie internetowej, trasa prowadzi do miejsca/ekranu docelowego (ang. destination) i służy jako jego unikalny identyfikator. Miejsce docelowe to zazwyczaj pojedyncza funkcja kompozycyjna odpowiadająca temu, co widzi użytkownik. W naszej aplikacji mamy tylko 2 ekrany: ekran dodawania/edycji zadania i ekran listy zadań, ale mamy 3 trasy ponieważ funkcjonalność edycji różni się od funkcjonalności dodawania.

Jednym ze sposobów definiowania tras aplikacji jest wykorzystania typu wyliczeniowego. Klasy typu enum w Kotlinie mają właściwość name, która zwraca ciąg znaków z nazwą właściwości.

Zaczniemy od zdefiniowania naszych 3 tras. Przejdź do pliku ToDoListApp i dodaj następującą klasę enum:

ToDoListApp.kt
enum class ToDoAppDestinations() {
   List,
   Add,
   Edit
}
Wskazówka: Czasem do definiowania tras można wykorzystać klasy typu sealed. Jednak w tym przypadku łatwiejszym rozwiązaniem jest klasa typu enum.

Dodanie NavHost i kontrolera nawigacji
NavHost jest komponentem, który wyświetla ekrany docelowe w oparciu o daną trasę. Na przykład, jeśli trasa to List, NavHost wyświetli ekran z listą. Jeśli trasa to Add, aplikacja wyświetli ekran wprowadzania zadania.

Składnia NavHost jest taka sama jak każdej innej funkcji kompozycyjnej. Na szczególną uwagę zasługują jej dwa parametry:

navController: Instancja klasy NavHostController wykorzystywana do nawigacji między ekranami, na przykład wywołując metodę navigate()
startDestination: Trasa definiująca początkowe miejsce docelowe w momencie uruchomienia aktywności.
Informacja: NavHostController jest podklasą klasy NavController, która zapewnia dodatkową funkcjonalność do użytku z funkcją NavHost.

Dodajmy NavHost oraz NavHostController do funkcji kompozycyjnej ToDoListApp. W pierwszej kolejności zmienimy sygnaturę funkcji ToDoListApp tak by inicjować w niej kontroler nawigacji wykorzystując funkcję rememberNavController() :

ToDoListApp.kt
@Composable
fun ToDoListApp(
   navController: NavHostController = rememberNavController()
)
Następnie możemy dodać NavHost, do którego przekażemy navController. W przypadku tej aplikacji NavHost będzie jeszcze dodatkowo umieszczony w elemencie Scaffold, który umożliwia łatwe dodanie często wykorzystywanych elementów UI takich jak: FloatingActionButton czy Topbar. Do funkcji ToDoListApp dodaj:

ToDoListApp.kt
Scaffold(
   topBar = {},
   floatingActionButton = {},
   floatingActionButtonPosition = FabPosition.End
) { innerPadding ->
   NavHost(
       navController = navController,
       startDestination = ToDoAppDestinations.List.name,
       modifier = Modifier
           .fillMaxSize()
           .padding(innerPadding)
   ) {
   }
}
Wskazówka: Zwróć uwagę na sposób wykorzystania typu wyliczeniowego do uzyskania ciągu znaków trasy we właściwości startDestination

Definicja przejść pomiędzy ekranami
Element NavHost powinien zawierać zbiór wywołań funkcji composable(), które służą do określenia miejsc docelowych. Funkcja composable posiada 2 wymagane parametry:

route: Ciąg znaków odpowiadający nazwie trasy. Może to być dowolny unikalny ciąg znaków, ale dobrą praktyką jest przechowywanie tras w typie wyliczeniowy,
content: miejsce w którym wywołujemy funkcję kompozycyjną, którą chcemy wyświetlić dla danej trasy. Zazwyczaj jest przekazywany w formacie trailing lambda.
W naszej aplikacji wywołamy trzy funkcje composable. Dodaj następujący kod w NavHost:

ToDoListApp.kt
composable(route = ToDoAppDestinations.List.name) {
   ToDoListScreen(
       onEdit = { }
   )
}
composable(route = ToDoAppDestinations.Add.name) {
   AddEditScreen(
       onSave = {},
       onCancel = {}
   )
}
composable(route = ToDoAppDestinations.Edit.name) {
   AddEditScreen(
       task = null,
       onSave = {},
       onCancel = {}
   )
}
Wskazówka: Funkcje composable działają trochę jak wyrażenie when z parametrem route. W zależności od wartości route wybranie zostanie odpowiedni ekran do wyświetlenia.

Posiadając zdefiniowane funkcje composable możemy wykonać pierwsze przejście między ekranami. W tym celu posłużymy się parametrem floatingActionButton ze Scaffold, który umożliwia dodanie tzw. pływającego przycisku. Zmień wywołanie funkcji Scaffold na następujące:

ToDoListApp.kt

W kodzie tym dodano wywołanie funkcji kompozycyjnej FloatingActionButton, która zwyczajowo składa się tylko z ikony, w tym przypadku to ikona Add. Kliknięcie w ten przycisk realizuje kod:

 navController.navigate(ToDoAppDestinations.Add.name)
Wywołujemy tutaj metodę navigate ze zmiennej navController przekazując nazwę trasy jako argument. Gdy trasa odpowiada jednemu z wywołań funkcji composable() w NavHost, aplikacja przechodzi do tego ekranu.

Aby przetestować działanie tego przejścia musimy zmodyfikować zawartość setContent w klasie MainActivity:

Samo przejście powinno działać poprawnie ale nie mamy jeszcze reakcji na przyciski save i cancel.

Wykorzystamy w tym celu funkcje lambda będące parametrami ekranu AddEditScreen. Znajdź funkcję composable dla ścieżki Add i dodaj implementacje funkcji onSave i onCancel:

ToDoListApp.kt
AddEditScreen(
   onSave = {
       DataSource.addTask(it)
       navController.navigateUp()
   },

W funkcji onSave parametrem jest instancja obiektu klasy Task (reprezentowana przez zmienną it), którą możemy zapisać w obiekcie DataSource za pomocą metody addTask. Zarówno w przypadk zapisu jak i anulowania tworzenia zadania użytkownik spodziewałby się powrotu do ekranu listy. W powyższym kodzie jest to zrealizowane za pomocą metody navigateUp z navController. Metoda ta zdejmuje z tzw. stosu wstecznego (ang. back stack) obecnie wyświetlany ekran i powraca do poprzedniego, w tym przypadku będzie to ekran listy.

Sprawdź czy dodawanie zadań i przycisk cancel działają poprawnie.

Przekazywanie argumentów
W następnych krokach zajmiemy się przejściem do ekranu edycji. Ekran ten jest inny od pozostałych ponieważ wymaga on przekazania argumentu umożliwiającego dostęp do zadania do edycji.

Argumenty do funkcji composable można dodać przez parametr arguments, który umożliwia przekazanie listy argumentów do ekranu docelowego. Każdy element tej listy powinien być stworzony za pomocą funkcji navArgument, której parametrami są: nazwa oraz funkcja tworząca zmienną typu NavArgument, która umożliwia określenie typu przekazywanej zmiennej oraz jej domyślnej wartości (opcjonalnie).

W naszym przypadku będzie to pojedynczy argument będący identyfikatorem zadania do edycji (typu Long) .

Zmodyfikuj funkcję composable dla ścieżki Edit:

ToDoListApp.kt
composable(
   route = ToDoAppDestinations.Edit.name + "/{taskToEditId}",
   arguments = listOf(navArgument(name = "taskToEditId") {
       type = NavType.LongType
   })
) { backStackEntry ->
   val taskToEditId = backStackEntry.arguments?.getLong("taskToEditId")
   taskToEditId ?: return@composable
   val task = DataSource.getTask(taskToEditId)

   AddEditScreen(
       task = task,
       onSave = {
           DataSource.updateTask(it)
           navController.navigateUp()
       },
       onCancel = {
           navController.navigateUp()
       })
}
Wskazówka: Zwróć uwagę na przekazanie drugiego z parametrów funkcji navArguments z wykorzystaniem trailing lambda. Typ argumentu definiowany jest za pomocą obiektu NavType

Dodanie argumentów do funkcji composable wiąże się jeszcze z koniecznością modyfikacji parametru route, w którym do głównej trasy musimy dodać listę nazw argumentów w nawiasach {} przedzielonych symbolami "/".

Odczyt przekazywanych elementów jest możliwy wykorzystując zmienna typu NavBackStackEntry przekazywaną do funkcji kompozycyjnej będącej zawartością funkcji composable. W przypadku kodu powyżej jest to zmienna backStackEntry z której za pomocą właściwości arguments możemy pobrać przekazane dane wykorzystując wbudowane metody. W tym przypadku wykorzystana jest metoda getLong (argument jest typu Long) z nazwą argumentu, który chcemy odczytać. Na podstawie wartości zmiennej taskToEditId (o ile jej wartość nie jest null) możemy z obiektu DataSource pobrać odpowiednie zadanie do edycji wywołując metodę getTask. Pobrane zadanie jest następnie przekazywane do funkcji kompozycyjnej AddEditScreen, która użyje dane z tej zmiennej do wstępnego wypełnienia formularza. Funkcje lambda onSave i onCancel są zaimplementowane podobnie jak w przypadku ekranu dodawania z tą różnicą, że zamiast wywołania metody addTask wywoływana jest metoda updateTask.

9. Baza danych
Podczas tworzenia aplikacji z listą zadań konieczne jest trwałe przechowywanie danych tak, aby były one dostępne po zamknięciu i ponownym otwarciu aplikacji. W tym celu możemy użyć biblioteki Room systemu Android, która zapewnia warstwę abstrakcji nad SQLite, upraszczając tworzenie bazy danych i dostęp do niej, zapewniając jednocześnie bezpieczeństwo typu i łatwość użytkowania. Room automatycznie obsługuje zapytania i aktualizacje bazy danych za pomocą adnotacji. Używa adnotacji (@Entity, @Dao, @Database) do definiowania tabel i zapytań.

Stworzenie encji (tablicy) Room

Stworzenie obiektu dostępu do danych (DAO, Data Access Object)
Kolejnym krokiem jest utworzenie obiektu dostępu do danych (DAO). DAO definiuje metody dostępu do bazy danych. Działanie DAO polega na ukryciu wszystkich zawiłości związanych z wykonywaniem operacji na bazie danych w tzw. warstwie trwałości (ang. persistance layer), oddzielonej od reszty aplikacji. Pozwala to na zmianę warstwy danych niezależnie od kodu, który korzysta z danych.

źródło: Persist data with Room

Stworzenie DAO, to stworzenie interfejsu z adnotacją @Dao. Interfejs ten zapewnia metody odpytywania/pobierania, wstawiania, usuwania i aktualizowania bazy danych. Metody te będą korzystać z adnotacji Room, takich jak @Insert, @Update, @Delete i @Query. Room generuje implementację tej klasy w czasie kompilacji.

Interfejs DAO umieścimy w nowej paczce nazwanej database. Dodaj ją do projektu:



następnie utwórz w niej nowy plik:



ToDoDao.kt
/**
 * Data access object for the [ToDoDatabase].
 */
@Dao
interface ToDoDao {
    /**
     * Insert a task into the database.
     * If the task already exists, replace it ([OnConflictStrategy.REPLACE]).
     * @param task the task to insert
     */
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertTask(task: Task)

    /**
     * Update a task in the database.
     * @param task the task to update
     */
    @Update
    suspend fun updateTask(task: Task)

    /**
     * Delete a task from the database.
     * @param task the task to delete
     */
    @Delete
    suspend fun deleteTask(task: Task)

    /**
     * Get all tasks from the database. The returned list of tasks is a [Flow] that will be
     * automatically updated when the underlying data changes and can trigger recompositions.
     * @return a [Flow] of list of tasks
     */
    @Query("SELECT * FROM todo_tasks")
    // @QUERY annotation specifies the SQL query to get all tasks (*) from the todo_tasks table
    fun getAllTasks(): Flow<List<Task>>

    /**
     * Get a task by its ID from the database. The returned task is a [Flow] so that it can be
     * observed for changes and trigger recompositions.
     * @param taskId the ID of the task to get
     * @return a [Flow] of a task
     */
    @Query("SELECT * FROM todo_tasks WHERE taskId = :taskId")
    // WHERE in the SQL query allows to filter the tasks by the taskId column. The :taskId is a
    // placeholder that will be replaced by the actual taskId value when the query is executed.
    fun getTaskById(taskId: Long): Flow<Task?>
}
Uwaga: Zaimportuj brakujące zależności. Dla Flow wybierz:



W powyższym kodzie przeznaczenie funkcji insertTask, updateTask i deleteTask nie wymaga wyjaśnień, ale należy zwrócić uwagę na dwie rzeczy. Po pierwsze wszystkie te metody oznaczone są słowem kluczowym suspend, jest to specjalne oznaczenie dla funkcji, które mają być realizowane w tle. Operacje na bazie danych mogą trwać długo, więc muszą być wykonywane w osobnym wątku. Room nie pozwala na dostęp do bazy danych w głównym wątku. Jak wywoływać funkcje oznaczone jako suspend zostanie pokazane w dalszej części instrukcji.

Drugim elementem, który wymaga uwagi to parametr adnotacji @Insert onConflict. Wartość tego parametru określa sposób rozwiązywania konfliktu przy wstawianiu nowych elementów, w naszym przypadku będzie to zamiana zadania. Sprawdź jakie jeszcze sposoby rozwiązywania konfliktów są przewidziane w obiekcie onCoflictStrategy.

Do odczytu wpisów z bazy służy adnotacja @Query, w której przekazujemy zapytania SQLite. Najprostszym zapytaniem jest zapytanie w metodzie getAllTasks: @Query("SELECT * FROM todo_tasks"), które mówi: pobierz wszystkie wpisy (*) z tablicy o nazwie todo_tasks.

Jeżeli chcemy przekazać jakieś wartości do zapytania to przykład przedstawia metoda getTaskById gdzie w zapytaniu @Query("SELECT * FROM todo_tasks WHERE taskId = :taskId") skorzystaliśmy dodatkowo ze słowa kluczowego WHERE pozwalającego filtrować tablice na podstawie warunków. W tym przypadku argument metody getTaskById taskId jest przekazywany do zapytania SQLite przez dodanie symbolu ":". Zapytanie to zwróci pojedynczy wpis w tabeli o zadanym taskId (o ile taki wpis istnieje)

W przypadku korzystania z zapytań @Query zaleca się używanie interfejsu Flow. Zwracanie wartości przez zapytanie w postaci Flow umożliwia powiadomienie za każdym razem, gdy dane w bazie danych ulegną zmianie. Room aktualizuje Flow, co oznacza, że wystarczy wywołać taką metodę tylko raz i obserwować zmiany. Metody zwracające Flow uruchamiają zapytanie w tle. Nie ma więc potrzeby tworzenia funkcji oznaczonej jako suspend, jak to miało miejsce np. przy @Insert.

Stworzenie klasy RoomDatabase
Po zdefiniowaniu encji i DAO możemy utworzyć klasę RoomDatabase. Klasa ta zawiera wersję bazy danych i encje, którymi zarządza. Klasa RoomDatabase udostępnia aplikacji instancje DAO. Z kolei aplikacja może używać DAO do pobierania danych z bazy danych.

Ogólny proces tworzenia instancji RoomDatabase przebiega następująco:

Utwórz publiczną klasę abstrakcyjną (abstract class), która rozszerza RoomDatabase. Klasa jest abstrakcyjna, ponieważ biblioteka Room stworzy jej implementację.
Opatrz klasę adnotacją @Database. W argumentach wymień encje dla bazy danych i ustaw numer wersji.
Zdefiniuj abstrakcyjną metodę lub właściwość, która zwraca instancję DAO.
Potrzebujemy tylko jednej instancji RoomDatabase dla całej aplikacji, więc RoomDatabase powinna być singletonem.
Aby utworzyć bazę danych wykorzystujemy Room.databaseBuilder, ale tylko wtedy, gdy nie istnieje. W przeciwnym razie zwracamy istniejącą bazę danych.
Dodajmy teraz następującą klasę do pakietu database:



ToDoDatabase.kt
/**
 * The Room database for this app. It is a singleton that provides a database instance.
 * This code is a standard way to create a Room database and is often reused in other apps.
 * @Database annotation specifies the entities (tables in the database) and the version of the database.
 * When you change the entity class you should update the version number.
 */
@Database(entities = [Task::class], version = 1)
abstract class ToDoDatabase() : RoomDatabase() {
    // The access to the data is done through the DAO (Data Access Object) interface.
    abstract fun dao(): ToDoDao

    /**
     * A companion object to create the database instance.
     * The companion object is a singleton that is created when the class is loaded.
     * It is used to create the database instance and make sure that only one instance is created.
     */
    companion object {
        // The name of the database
        const val DATABASE_NAME = "todo_database"

        // Variable to hold the database instance. The @Volatile annotation means that the access
        // to the variable is always atomic and the write operations are
        // done in such a way that it is visible to all threads.
        @Volatile
        private var INSTANCE: ToDoDatabase? = null

        /**
         * Get the database instance.
         * @param context the application context - required to create the database
         * @return the database instance
         */
        fun getDatabase(context: Context): ToDoDatabase {
           // If the instance is null, create a new database instance in a synchronized way
            // to make sure that only one thread can access it at a time.
            return INSTANCE ?: synchronized(this) {
                // create a new database instance - this is a standard way to create a Room database
                Room.databaseBuilder(
                    context.applicationContext,
                    ToDoDatabase::class.java,
                    DATABASE_NAME
                ).fallbackToDestructiveMigration()
                    .build().also { INSTANCE = it }
                // the also function is used to execute a block of code on the object that is being
                // created and return the object itself.
            }
        }
    }
}

Informacja: Jest to standardowe podejście do tworzenia klasy bazy danych. Kod ten można używać w wielu projektach, trzeba tylko pamiętać o zmianie: nazw, encji i dao

Tak jak opisano w procedurze powyżej, klasa ToDoDatabase:

Dziedziczy z RoomDatabase i jest klasą abstrakcyjną
posiada adnotację @Database, definiując encje i wersję bazy danych.
posiada abstrakcyjną funkcję dla DAO: abstract fun dao(): ToDoDao
Posiada element companion object ze zmienną INSTANCE oznaczoną jako @Volatile, aby zapewnić bezpieczeństwo wątków, zapobiegając tworzeniu wielu instancji bazy danych. W ten sposób mamy pewność, że będzie istnieć tylko jedna instancja bazy danych.
Używa Room.databaseBuilder() do utworzenia instancji bazy danych, która jest pobierana za pomocą metody getDatabase().
Podczas tworzenia bazy danych Room używana jest funkcja synchronized, aby zapewnić, że tworzona jest tylko jedna instancja bazy danych, nawet jeśli dostęp do niej uzyskuje wiele wątków. Metoda databaseBuilder wymaga przekazania kontekstu aplikacji, klasy bazy danych i jej nazwy. Dodatkowo musimy określić strategie przenoszenia danych (ang. migration) w tym przypadku jest to fallbackToDestructiveMigration, co umożliwia Room destrukcyjne odtworzenie tabel bazy danych, jeśli schematy migracji danych nie zostaną znalezione. Funkcja also pozwala na przypisanie stworzonego obiektu do zmiennej INSTANCE i jednoczesne jego zwrócenie w funkcji getDatabase

Informacja: Zazwyczaj należy dostarczyć obiekt migracji ze strategią migracji w przypadku zmiany schematu. Obiekt migracji to obiekt, który definiuje sposób pobierania wszystkich wierszy ze starego schematu i konwertowania ich na wiersze w nowym schemacie, tak aby żadne dane nie zostały utracone.
10. Repozytorium i korutyny
W aplikacjach korzystających z baz danych często korzysta się z jeszcze jednej warstwy abstrakcji nad bazą danych w postaci repozytorium. Repozytorium to wzorzec projektowy zapewnianiający interfejs do uzyskiwania dostępu do danych. Pomaga oddzielić logikę danych od interfejsu użytkownika i sprawia, że aplikacja jest łatwiejsza w utrzymaniu i testowaniu. Repozytorium pozwala też na łatwiejsze wykorzystanie mechanizmu współbieżności (w Kotlin tzw. Korutyn ) do realizacji zadań w tle.

Korutyny (ang. Coroutines) to prosty sposób na wykonywanie operacji asynchronicznych w Kotlinie, przez co są kluczowe w aplikacjach do obsługi zadań, takich jak żądania sieciowe, operacje na bazach danych czy intensywne obliczenia.

Stosowanie korutyn niesie wiele korzyści. Po pierwsze unikamy w ten sposób blokowania wątku interfejsu użytkownika (tzw. main thread lub UI thread) - zapewnia to możliwość interakcji użytkownika UI przy wykonywaniu innych operacji. Po drugie korutyny są świadome cyklu życia i zapobiegając wyciekom pamięci. Są też łatwiejsze w zarządzaniu niż zwykłe wątki (klasa Thread), nie trzeba się przejmować złożoną logiką ręcznego wywoływania wątków.

Podstawową elementem korutyn jest interfejs CoroutineScope, który zarządza ich cyklem życia. Zapewnia przestrzeń, w której można uruchamiać korutyny, zapewniając, że są one prawidłowo anulowane, gdy nie są już potrzebne.

Do uruchamiania korutyn służą funkcję launch i async, które z kolei mogą wywoływać funkcję oznaczone jako suspend. Funkcja suspend to taka, która może zostać wstrzymana i wznowiona bez blokowania głównego wątku. Można ją wywołać tylko z innej funkcji suspend lub wewnątrz korutyny. Funkcja launch uruchamia zadanie bez oczekiwania na jego wynik (wykonanie asynchroniczne). Jest powszechnie używana, gdy nie interesuje nas zwracana wartość np. zapisywanie danych do bazy danych. Funkcja async jest wykorzystywana w parze z funkcją await i służy do uruchamiania zadania z oczekiwaniem na zwracaną wartość. Funkcja await jest wykorzystywana do odzyskania wyniku z korutyny.

Kolejnym istotnym elementem systemu korutyn są obiekty dyspozytorów (ang. dispatchers), które służą do określenia, na którym wątku dane zadanie ma być uruchomione. Dostępne są następujące implementacje, zoptymalizowane pod kątem określonego rodzaju pracy:

Dispatchers.Main: Uruchamiany w głównym wątku UI (używany do aktualizacji UI).
Dispatchers.IO: Zoptymalizowany dla operacji I/O (baza danych, sieć, operacje na plikach).
Dispatchers.Default: Używany do zadań wymagających dużej mocy obliczeniowej procesora (sortowanie, obliczenia).
Dispatchers.Unconfined: Uruchamia się w bieżącym wątku, ale może zostać przeniesiony do innego wątku.
W wywołaniu launch możemy określić rodzaj dyspozytora, ale często stosowana jest funkcja withContext, która pozwala na zmianę dyspozytora w ramach pojedynczego zadania.

W kontekście tworzenia aplikacji z wykorzystaniem Compose do obsługi korutyn w ramach funkcji kompozycyjnych wykorzystywana jest zasadniczo metoda rememberCoroutineScope, ale istnieje też podejście wykorzystujące funkcję kompozycyjną LaunchEffect. Główna różnica polega na tym, że LaunchEffect jest wywoływana za każdym razem, gdy argument key do niej przekazywany się zmieni. W przypadku remeberCoroutineScope rekompozycje nie będą powodować automatycznego wywołania zadania realizowanego w ramach CoroutineScope i jest to rozwiązanie przewidziane na wywoływanie zadań w tle odpowiedzi na zdarzenia wyzwolone przez UI.

Przejdźmy teraz do wykorzystania powyższej wiedzy w praktyce.

Definicja repozytorium
Rozpoczniemy od stworzenia klasy repozytorium. W paczce database utwórz plik:



ToDoRepository.kt
/**
* Repository class for the ToDoListApp
* It provides an abstraction layer over the data source (the database)
* and manages the data operations.
* @param dao the data access object for the database
*/
class ToDoRepository(private val dao: ToDoDao) {
   /**
    * A flow of tasks from the database.
    * The flow will be automatically updated when the underlying data changes
    * and can trigger recompositions.
    */
   val tasksFlow = dao.getAllTasks()
   /**
    * Get a task [Flow] by its ID from the database.
    * @param taskId the ID of the task to get
    * @return a task [Flow]
    */
   fun getTaskById(taskId: Long) = dao.getTaskById(taskId)
   /**
    * Add a task to the database.
    * @param task the task to add
    */
   suspend fun addTask(task: Task) {
       // The operation is done in the IO dispatcher to avoid blocking the UI thread - IO
       // operations are optimized for disk and network operations.
       withContext(Dispatchers.IO) {
           dao.insertTask(task)
       }
   }
   /**
    * Update a task in the database.
    * @param task the task to update
    */
   suspend fun updateTask(task: Task) {
       withContext(Dispatchers.IO) {
           dao.updateTask(task)
       }
   }
   /**
    * Delete a task from the database.
    * @param task the task to delete
    */
   suspend fun deleteTask(task: Task) {
       withContext(Dispatchers.IO) {
           dao.deleteTask(task)
       }
   }
}
Klasa posiada konstruktor, w którym określamy powiązanie z obiektem DAO bazy danych, który jest wykorzystany w zdefiniowanych w repozytorium funkcjach oraz właściwościach.

Funkcje addTask, updateTask, i deleteTask są funkcjami typu suspend, które wywołują odpowiednie metody z interfejsu DAO w dyspozytorze IO.

Funkcje pobierania danych różnią się od tych służących do modyfikacji bazy. Wykorzystano tutaj interfejs Flow, który w wygodny sposób pozwala obserwować zmiany w bazie danych dla określonych zapytań. W funkcji getAllTasks z dao nie ma parametrów stąd możemy zwracany Flow przypisać do właściwości repozytorium. W przypadku funkcji getTaskById musimy przekazać identyfikator zadania, które chcemy odczytać stąd jest to realizowane przez osobą funkcję.

Często spotykaną praktyką związaną z repozytorium jest stworzenie pojedynczej instancji repozytorium i korzystanie tylko z niej jak we wzorcu singleton. Jest to podstawowa klasa, która utrzymuje globalny stan aplikacji. Jest tworzona przed jakąkolwiek aktywnością, usługą lub innym komponentem i istnieje przez cały okres istnienia aplikacji. /**
* Application class for the ToDoListApp
* It initializes the ToDoRepository - the single source of truth for the app
*/
class ToDoListApplication: Application() {

   // The repository is initialized when the application is created
   // with the lateinit keyword to make sure it is initialized before it is used
   lateinit var toDoRepository: ToDoRepository
       private set // The setter is private to prevent other classes from modifying the repository

   override fun onCreate() {
       super.onCreate()
       // Initialize the repository by getting the instance of the database
       // and passing its dao to the repository
       toDoRepository = ToDoRepository(ToDoDatabase.getDatabase(this).dao())
   }
}
Klasa posiada tylko pojedynczą właściwość toDoRepository, która ma publiczny getter i prywatny setter. Dodatkowa właściwość jest oznaczona słowem lateinit. 11. System Intencji - uruchamianie innych aplikacji
W kontekście nawigacji w aplikacjach, zarówno w ramach własnej jak i innych aplikacji, wykorzystywany jest mechanizm tzw. intencji. Intencja (ang. Intent) to obiekt do przesyłania wiadomości, który umożliwia komunikację między komponentami aplikacji oraz między różnymi aplikacjami. Służy do uruchamiania aktywności i innych komponentów aplikacji takich jak usługi (ang. Services) oraz odbiorniki wiadomości rozsiewczych (ang. Broadcast Receivers).

Istnieją dwa rodzaje intencji. Intencja jawna (ang. explicit) służąca do uruchamiania jasno określonych komponentów np. określoną aktywność (jawnie określamy jaka klasa ma być uruchomiona). Drugi rodzaj intencji to intencje niejawne (ang. implicit), które służą do uruchamiania komponentów kiedy nie znamy jego dokładnej nazwy, ale chcemy wykonać jakąś akcję. System Android na podstawie systemu filtrów decyduje jakie komponenty aplikacji są w stanie obsłużyć daną intencję. Filtry określane są w pliku manifest każdej aplikacji. Przykładem filtru jest:

AndroidManifest.xml
<activity
   android:name=".MainActivity"
   android:exported="true"
   android:label="@string/app_name"
   android:theme="@style/Theme.ToDoListApp">
   <intent-filter>
       <action android:name="android.intent.action.MAIN" />

       <category android:name="android.intent.category.LAUNCHER" />
   </intent-filter>
</activity>
Informacja: Więcej o intencjach można znaleźć w dokumentacji: Intents and intent filters | App architecture | Android Developers

W naszej aplikacji wykorzystamy niejawną intencje z akcją wysyłania wiadomości. Pozwoli to na stworzenie wiadomości np. e-mail, którą będzie można przesłać dalej. Funkcjonalność ta będzie dostępna z górnego paska ekranu ToDoApp.

Przejdź do pliku ToDoApp i utwórz w nim następującą funkcję (poza wszystkimi funkcjami kompozycyjnymi):

ToDoListApp.kt
private fun sendList(context: Context, listString: String) {
   val intent = Intent(Intent.ACTION_SEND).apply {
       type = "text/plain"
       putExtra(Intent.EXTRA_SUBJECT, "ToDo List")
       putExtra(Intent.EXTRA_TEXT, listString)
   }
   context.startActivity(intent)
}
Funkcja ma 2 parametry, pierwszy to kontekst aplikacji potrzebny do uruchomienia intencji, a drugi to lista zadań w postaci przekonwertowanej na String. W kodzie tym tworzymy najpierw intencje z akcją ACTION_SEND (jest to jedna z wbudowanych akcji), w której dodatkowo określamy format przesyłanych danych poprzez element type oraz zawartość i temat poprzez tzw. pola extra intencji (metoda putExtra). Te dodatkowe dane są przesyłane w postaci klucz (nazwa) i wartość podobnie jak ma to miejsce w przypadku przekazywania argumentów pomiędzy funkcjami composable w Komponencie Nawigacji. W przypadku akcji ACTION_SEND klucze identyfikujące dodatkowe dane są z góry zdefiniowane w klasie Intent (np. EXTRA_TEXT).

Informacja: Więcej typowych akcjach można znaleźć w dokumentacji: Intents and intent filters | App architecture | Android Developers

Stworzoną intencję (zmienna intent) wykorzystujemy w metodzie startActivity z klasy Context. Jak sama nazwa wskazuje służy ona do uruchamiania aktywności. Wywołanie tej metody spowoduje wyszukanie przez system wszystkich aplikacji, które mogą obsłużyć taką intencję, po czym, gdy jest ich więcej niż jedna, pozwoli użytkownikowi wybrać jedną z opcji. Dane przekazane przez pola extra, będą mogły być odczytane przez docelową aplikację.

Zanim wykorzystamy powyższą funkcję dodajmy jeszcze jedną funkcję, tym razem w pliku Task:

/**

  return buildString {
       append("Tasks:\n")
       tasks.forEach {
           append("${it.name}\n${it.description}\n")
           append("Completed: ${it.isCompleted}\n")
           append("Important: ${it.isImportant}\n")
           append("Task ID: ${it.taskId}\n")

       actions = {
           val tasks by repository.tasksFlow.collectAsState(initial = emptyList())
           IconButton(
               onClick = {
                   if(tasks.isNotEmpty()) {
                       val listString = convertToString(tasks)
                       sendList(context, listString)
                   }
               },
               colors = IconButtonDefaults.iconButtonColors(contentColor = colorScheme.primary)
           ) {
               Icon(imageVector = Icons.Outlined.Email, contentDescription = "Send list via email")
           }
       },
       modifier = modifier.padding(start = 8.dp, end = 8.dp)
   )
}
Główna zmiana w tej funkcji to dodanie parametru actions w TopAppBar pozwalającego na zdefiniowanie dodatkowych funkcji w ramach górnego paska. W tym przypadku dodaliśmy pojedynczy przycisk z ikoną Email, po kliknięciu, którego lista wszystkich zadań pobierana jest z bazy danych wykorzystując repozytorium przekazane w parametrze (podobnie jak to miało miejsce w przypadku ekranu z listą). Następnie lista (o ile nie jest pusta) jest konwertowana na postać pojedynczego ciągu znaków z wykorzystaniem wcześniej przygotowanej funkcji, której wynik przekazywany jest do funkcji sendList. Funkcja sendList wymaga referencji do obiektu Context, stąd na początku funkcji ToDoListTopBar stworzyliśmy zmienną context i przepisaliśmy jej wartość z LocalContext.current (jest to typowy sposób na dostęp do kontekstu z poziomu funkcji kompozycyjnej).

12. Animacje
Ostatnim zagadnieniem w tym ćwiczeniu będzie dodanie efektów wizualnych w postaci animacji wbudowanych w narzędzia Compose.

Więcej o animacjach można znaleźć w dokumentacji:

Quick guide to Animations in Compose | Jetpack Compose | Android Developers

Animacje pojedynczego elementu listy
Rozpoczniemy od animacji dotyczących pojedynczego elementu listy. Animacje wykorzystamy do:

zmiany koloru tła w przypadku ukończenia zadania,
zmiany rozmiaru elementu w reakcji na rozwinięcie zadania
obrotu "strzałki" wskazującej stan rozwinięcia zadania
Do funkcji kompozycyjnej TaskItem (plik ToDoListScreen.kt) dodaj następujące zmienne:

ToDoListScreen.kt
val rotationAngle by animateFloatAsState(
   targetValue = if (expanded) 180f else 0f,
   animationSpec = tween(durationMillis = 500),
   label = "Chevron Rotation"
)

val contentHeight by animateDpAsState(
   targetValue = if (expanded) (3 * 56).dp else 56.dp,
   animationSpec = spring(
       stiffness = Spring.StiffnessLow,
       dampingRatio = Spring.DampingRatioMediumBouncy
   ),
   label = "Content Height Animation"
)

val surfaceColor by animateColorAsState(
   targetValue = if (task.isCompleted)
       MaterialTheme.colorScheme.secondary.copy(alpha = 0.75f) else MaterialTheme.colorScheme.surface,
   animationSpec = tween(durationMillis = 500),
)
Do animacji właściwości funkcji kompozycyjnych można wykorzystać metody animate...AsState. W naszym przypadku:

w zmiennej rotationAngle zmieniamy wartość Float określającą kąt obrotu elementu, w którym ta animacja będzie użyta. Kąt będzie się zmieniał z 0 do 180 i vice versa
w zmiennej contentHeight zmieniamy rozmiar w jednostkach dp. Rozmiar będzie się zmieniał w zakresie od 56 dp do 3*56 dp. Ustawienie maksymalnej wysokości na stałą wartość może się wiązać z koniecznością dodania modyfikatora verticalScroll do elementu wyświetlającego opis zadania.
w zmiennej surfaceColor zmieniamy kolor, z domyślnego (MaterialTheme.colorScheme.surface) do koloru typu secondary ze zmodyfikowaną przezroczystością.
We wszystkich przypadkach wartości docelowe zmian są określone w parametrze targetValue. Natomiast sposób zmian jest określony w animationSpec. Wykorzystano tu dwa rodzaje wbudowanych animacji: spring i tween. Spring pozwala na stworzenie animacji wykorzystujących fizykę sprężystych materiałów. Natomiast tween jest płynną animacją wartości. W przypadku spring możemy określić sztywność materiału (parametr stiffness) oraz stopień tłumienia (dampingRatio). Jak działają oba parametry można podejrzeć na nagraniach:

https://developer.android.com/static/develop/ui/compose/images/animations/damping_ratio.mp4

https://developer.android.com/static/develop/ui/compose/images/animations/stiffness_annotated.mp4

W przypadku animacji typu tween określamy tylko czas trwania animacji w milisekundach przez ustawienie parametru durationMillis.

Użyj tych zmiennych w odpowiednich elementach funkcji TaskItem:

contentHeight i surfaceColor może być użyte w Surface w następujący sposób:
ToDoListScreen.kt
Surface(
   modifier = modifier
       .fillMaxWidth()
       .padding(8.dp)
       .combinedClickable(
           onClick = { expanded = !expanded },
           onLongClick = onDelete // Long press to delete
       )
       .height(contentHeight),
   color = surfaceColor,
   shape = RoundedCornerShape(12.dp),
   shadowElevation = 4.dp
)
rotationAngle może być użyte w elemencie:
ToDoListScreen.kt
Icon(
   imageVector = Icons.Default.KeyboardArrowDown,
   contentDescription = "Expand",
   modifier = Modifier
       .size(24.dp)
       .rotate(rotationAngle)
)
Uruchom aplikację i sprawdź czy animacje działają.

Animacje listy
Innym rodzajem animacji, które możemy dodać są animacje całej listy. Wykorzystamy specjalny modyfikator: Modifier.animateItem w którym możemy określić animacje dla pojawiania, znikania i rozmieszczania elementów. By te animacje działały trzeba jeszcze dodatkowo wykorzystać parametr key w funkcji items, który jest wykorzystany do identyfikacji elementów. Zmodyfikuj kod dotyczący LazyColumn w funkcji ToDoListScreen:

ToDoListScreen.kt
LazyColumn(
   modifier = Modifier
       .weight(1f)
       .padding(bottom = 8.dp)
) {
   items(
       items = tasks,
       key = { it.taskId }
   ){ task ->
       TaskItem(
           task = task,
           onEditClick = { onEdit(task) },
           onDelete = {
               showDeleteDialog = true
               taskToDelete = task
           },
           onCheckedChange = {
               coroutineScope.launch {
                   repository.updateTask(task.copy(isCompleted = it))
               }
           },
           modifier = Modifier.animateItem(
               fadeInSpec = tween(2000),
               fadeOutSpec = spring(
                   stiffness = Spring.StiffnessLow,
                   dampingRatio = Spring.DampingRatioMediumBouncy
               ),
               placementSpec = spring(
                   stiffness = Spring.StiffnessLow,
                   dampingRatio = Spring.DampingRatioMediumBouncy
               )
           )
       )
   }
}
Parametr key ustawiony jest na identyfikator zadania, łączy to animacje z konkretnym elementem na liście. Do animacji pojawiania, znikania i rozmieszczania elementów wykorzystano wbudowane specyfikacje animacji spring i tween. Sprawdź działanie animacji. Animacja placementSpec jest widoczna w momencie usuwania elementów.
